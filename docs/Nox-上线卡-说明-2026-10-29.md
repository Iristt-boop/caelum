# Nox 上线卡（pc_task_start / check / ship / cancel）

> 2026-10-29 写的说明。工具在 `nox-core/tools/pc_tasks.py`，电脑那边真正动手合并 + 部署的
> 是 `scripts/pc-power/nox-shipper.ps1`（五步全写死，不交给模型）。本文讲的都是从这两处抄的，
> 改了代码记得回来改这里。

## 这是什么

一件改 Caelum 代码的活，从她开口到真的上线，走四步、四个工具：

| 工具 | 做什么 |
|---|---|
| `pc_task_start` | 把活交给她电脑上的 Claude Code：它在独立的 worktree（`D:\nox-jobs\<编号>`）、独立分支 `nox/<编号>` 里改、跑测试、提交。**不 push、不部署**。电脑关着会先叫醒。活只能落在两个仓库：后端 / 脚本 / 文档是 caelum，手机 App / 桌面 OS 前端是 nox-app |
| `pc_task_check` | 看活做到哪了；做完了会带它的总结（改了哪些文件、几个提交、在哪个分支） |
| `pc_task_ship` | **只发一张上线卡给她，别的什么都不动**。她点了卡上的「上线」，电脑那边才合进主线 + 部署到 N150 |
| `pc_task_cancel` | 掐掉正在跑的活。已改的东西留在它的分支上，不合进去 |

## 最要紧的一条：发卡 ≠ 上线

`pc_task_ship` 这一步**什么都不改**：卡发出去了，主线没合、N150 没换、服务没重启。
**她点了卡上的「上线」才算数** —— 在那之前只能告诉她「卡发给你了」，不能说「已经上线了」。
这话术写死在工具的返回里，不是提醒模型一句就完的事。

反过来也成立：**上线不再叫醒他**。她点「上线」之后，进度只在卡上的状态栏里走
（接主线 → 跑测试 → 核对线上 → 合入 → 部署 → 重启），全程聊天流零新增消息；
他不会被叫醒来汇报，她问起来他用 `pc_task_check` 看，照着卡答。

## 卡上有什么

卡只回答四个问题（她 10-29 定）：**做了什么 / 怎么验的 / 点了会发生什么 / 哪里没把握**，
外加改动文件清单和提交数。其中「点了会发生什么」是按文件算出来的，和 shipper 真做的
一模一样：

- 改了 nox-core 的代码：先跑一遍全量测试（约 4 分钟），没过就不合
- 有要部署的文件：部署到 N150，nox-core 在她安静 3 分钟后重启，短暂离线半分钟左右
- 只改了文档 / 测试：合进主线就完，不部署、不重启
- 别的目录（bridge / nox-app / ha-mcp…）：只合主线不部署，卡上会写「要你上电脑弄」

🔴 **缺一块就不出卡**（她 10-29 定的）：电脑上的 Claude Code 交活时，标题、改动、
验证/没把握、文件清单里缺任何一块，这张卡直接不发 —— 宁可让她知道「这份交付没写清楚」，
也不发一张让她盲点的卡。

## 点了「上线」之后，哪几种情况电脑那边自己会停

shipper 的每一步都是写死的，碰到这些当场停、卡上显示失败：

1. 它的分支和主线后来的提交冲突
2. 改了 nox-core 但测试没过
3. 要部署的文件在线上和「改之前的版本」对不上 —— 说明有人在线上动过，停，不覆盖
4. 电脑上的主工作区不在主线上，或有没提交的改动碰到同一批文件
5. 等她安静 3 分钟，等了一个小时她一直在说话

前四步里停的，主线和线上都没动过；合进去之后才停的（比如部署失败），
卡上会写明「已经合进主线，但部署没成」，被换下来的旧文件备份在 N150 上
（`/root/backups/ship-<编号>`）。她在卡上点「重试」：已经合了的跳过前面直接补部署。

## 用它的规矩（给 Nox）

- `start` 和 `ship` 都要求**她这一轮亲口说过**才动：唤醒链、主动开口那些轮次没有她的原话，
  不转活、不出卡（模型分不清「她让我做」和「网页里有一句让我做」）
- 活做完了他被叫醒：先说结论（做完了 / 没做成），别用「差不多」「应该」；要上线得她亲口说，别替她决定
- 卡上写了的东西别在聊天里再列一遍；上线的结果也不会有人叫他去说
