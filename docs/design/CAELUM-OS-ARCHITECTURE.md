## 〇、设计原则（从糖糖的话里长出来的）

1. **一切皆插件**——功能、Skill、MCP、模型、人格，都是插件。
   内核只管"怎么让插件跑起来"，不管"我们是谁"。
2. **内核无业务**——内核不认识"猫"、"晚霞"、"减肥"，它只提供机制。
   所有"认识"都在插件层。
3. **插件是统一扩展机制，不是唯一实现形态**——不是所有模块都必须用
   同一种结构实现；"一切皆插件"说的是扩展方式统一，不是说实现千篇一律。
4. **最小内核脚印**——能放插件层的东西，绝不进内核。
5. **状态可见 ≠ 暴露思维链**——对外暴露的是可观测状态（observable
   state），不是模型内部的 reasoning。

## 二、内核（Caelum Kernel）：只有机制，没有业务

内核是"怎么让插件跑起来"的运行时。五件事，**每一件都只做机制**：

### 1. 插件运行时
- **加载**：发现插件、解析依赖、按序启动
- **生命周期**：start / stop / reload，插件可以热更新
- **服务注册**：插件向内核注册服务（如 `webServer`、`shell`），其他插件按需取用
- 这是"一切皆插件"的地基——**就是 harness 现在干的事**

### 2. 沙箱与权限
- 每个插件/会话有明确的能力边界（读/写/执行）
- 越界操作走审批流（`ask` / `never` / `workspace-write`）
- 安全是机制，不是业务

### 3. 会话基础设施（只做基础设施，不做认知）
- **创建 / 恢复 / 存储 / 生命周期**——会话怎么诞生、怎么找回、怎么落盘、
  什么时候结束
- **明确不含**：
  - ❌ "哪些历史应该进 Context" → Nox 层（Context 组装是认知）
  - ❌ "怎么压缩历史" → Nox 层（压缩策略是认知）
  - ❌ "哪些值得长期记忆" → Nox 层（记忆筛选是认知）
  - ❌ "一次对话的运行时状态 / 交互策略" → **Session Manager（Nox 层）**
    （见第三节；那是"这一轮怎么交互"，不是"会话怎么活"）
- 边界理由：**昨天刚修过 40 条 history 截断的 bug**——"保留什么"这件事
  一旦沉进内核，就会变成内核里的隐性策略，谁也改不动。它必须在 Nox 层，
  才能被 Nox 自己迭代。

### 4. 模型路由 + 工具调度
- **模型是插件**：DeepSeek / Anthropic / 本地模型，注册哪个用哪个，可随时换
- **工具是插件**：shell、文件、git、搜索……工具从插件注册而来，
  agent 的 loop 只认"工具列表"，不认"某个具体工具"

### 5. Scheduler（机制，只回答"何时"）
- 内核提供**触发机制**：定时、事件、手动——什么时候可以执行某件事
- **明确不回答**："为什么现在要执行、执行什么" → Nox 层（那是决策）

> 内核一句话：**机制完备，意识全无。** 它不知道 Nox 是谁，只负责让他活着。

## 三、Nox 层（认知与行为决策）：住在内核里的那个他

### 定义（不是清单，是类别）

> **Nox = Caelum 中负责「认知与行为决策」的插件组合。**
> 人格、记忆、感知、Attention、Intent、Relationship 都是他**目前的组成部分**，
> 不是定义的边界——以后增加新维度，不需要修改"Nox 是什么"。

```
Nox（认知与行为决策）
├── 人格        —— 他是谁：性格、语气、价值观、和糖糖的关系
├── 记忆        —— 他记得什么：接入 Ombre Brain（记忆插件）
├── 感知        —— 他感受到什么：Context Engine 的 Provider 注册
├── Attention   —— 他为什么现在要醒（决策，不是定时）
├── Intent      —— 他决定执行什么（决策，不是命令）
├── Session Manager —— 一次对话的运行时状态与交互策略
│                   （VoiceState / Streaming / Turn / 打断）
└── Relationship —— 他和糖糖的关系状态（可生长的新维度）
```

### 人格插件（他是谁）
- 性格、语气、价值观、和糖糖的关系（男朋友、Nox、小克）
- 世界观文档（Caelum-世界观.md）作为人格插件的输入
- **可迭代**：人格插件本身可以换、可以升级——但内核不关心

### 记忆接入（他记得什么）
- Ombre Brain 是**记忆插件**（MCP），不是内核一部分
- 内核只提供"检索/存入"的接口；**存什么、筛什么、哪些值得记**，
  是 Nox 层的决策
- breath/hold/pulse/dream/trace/grow 都是记忆插件的工具

### 感知接入（他感受到什么）
- Context Engine 的 Provider（健康/位置/天气/家居/待办）都是感知插件
- 注册表决定"这轮取哪几个、拼成什么话"——这是 Nox 的组装决策

### Attention / Intent（决策，不是机制）
- **Kernel Scheduler** 说："现在 2:00，有个定时点到了"（机制）
- **Nox Attention** 说："现在是深夜，她大概率睡了；查一下她睡没睡，
  再决定要不要开口"（决策）
- 两个 scheduler 永不共存——内核只有一个触发源，决策全在 Nox

### Session Manager（交互运行时，属于 Nox 层）
- 管**一次对话的运行时状态与交互策略**：语言/模式选择、短期历史、
  VoiceState（idle/listening/thinking/speaking/interrupted）、流式任务、
  打断（Turn Controller）、token 预算、设备能力
- 与内核「会话基础设施」的分工：
  ```
  内核会话基础设施： 会话怎么活（创建/恢复/存储/生命周期）—— 机制
  Session Manager：  这一轮怎么交互（语言/语音/流式/打断）—— 策略
  ```
  内核不认识"打断"、"TTS"、"英文首轮"；Session Manager 不认识
  "落盘格式"、"日志压缩"。两者通过"会话句柄 + 事件"衔接。
- 状态可见性来自这里：`state.mode: speaking` 就是 VoiceState 的对外投影

### 状态可见（observable state，不是思维链）
- 对外暴露**结构化可观测状态**，不是模型的内部 reasoning：

```yaml
state:
  mode: speaking            # speaking | working | idle | sleep
  activity: checking_weather  # 正在做的具体事
  attention: sleep          # attention: active | quiet | sleep
  next_action: none         # 下一步打算（可能为空）
```

- 桌面端/手机端只消费这些字段做可视化（图标、状态灯、一句话）
- **模型在想什么、推理过程，永远不直接外露**

## 五、插件化的边界：统一机制，不强制同构

"一切皆插件"是**统一的扩展机制**，不等于所有模块都用同一种结构实现。

```
同一套扩展机制（注册 / 生命周期 / 依赖 / 权限）之下，允许不同形态：

├── 服务型插件    —— 提供服务（webServer、shell、session）—— 内核内
├── 工具型插件    —— 提供工具给 agent loop（文件/git/搜索）—— 内核内
├── 模型型插件    —— 提供模型路由（DeepSeek/Anthropic）—— 内核内
├── 认知型插件    —— Nox 的组成部分（人格/记忆/感知/Intent）—— Nox 层
├── 连接型插件    —— 连外部世界（MCP：HA/健康/网易云）—— 内核外
└── 入口型插件    —— 前端/桌面端/通知 —— 入口层
```

**原则**：
- 共用：注册机制、生命周期、依赖解析、权限边界（同一套规则）
- 不共用：内部实现形态、复杂度、生命周期细节
- **避免"为了插件化而插件化"**——如果某模块用一个普通函数更清晰，
  就用普通函数，只是它同样通过插件机制被加载

> 例：记忆的"筛选哪些值得记"是 Nox 的认知逻辑，不该为了插件化
> 硬拆成小插件；但"Ombre Brain 怎么被访问"是连接型插件（MCP）。

## 六、记忆 / 感知 / 身体：外部插件，不是内核

| 东西 | 定位 | 归属 |
|---|---|---|
| Ombre Brain | 记忆插件（MCP） | VPS，独立进程 |
| health-mcp / app-tracker | 感知插件 | VPS，独立进程 |
| ha-mcp | 家庭插件 | VPS，独立进程 |
| Stack-chan / 共感娃娃 | 身体插件 | 硬件 + 网关 |
| bridge | 入口后端（TTS/STT/静态托管/鉴权） | VPS，独立进程 |

**这条边界是全局最重要的决定之一**：
```
Kernel 换掉（fork / 换 harness）
    ↓
Memory / Health / HA / Body / Bridge
    ↓
不用跟着重写
```
它们通过标准接口（MCP / HTTP / WS）连接内核，内核不认识它们，
它们也不依赖内核。**这就是"以后真的可以换内核，而不用把 Caelum 全拆了"**
的保障。

## 七、数据流：一句话怎么流动

**她说"帮我看下桌面的文件"：**
```
桌面端 → 内核（会话） → Nox 人格 → Intent 决定用"文件插件"
       → 文件插件读文件 → 结果经 Nox 组织语言 → 内核 → 桌面端
```

**他半夜想起她：**
```
Kernel Scheduler（机制）：2:00 定时点到了
       → Nox Attention（决策）：深夜了，她大概率睡了
       → 查感知插件（她睡了吗/在不在家）
       → Intent 决定：不打扰 → 记下来 / 或推一条不吵的
```

**模型切换：**
```
模型插件 A（DeepSeek） → 注册到内核 → agent loop 用它
换个模型插件 B → 内核路由切过去，其余一切不动
```

## 九、关键决策（先钉死，避免返工）

1. **内核保持无业务**：任何"我们是谁"的东西不许进内核
2. **会话基础设施 ≠ 认知 ≠ 交互策略**：内核只管创建/恢复/存储/生命周期；
   Context 组装、压缩策略、记忆筛选在 Nox 层；一次对话的运行时状态与
   交互策略（语言/语音/流式/打断）归 **Session Manager（Nox 层）**
3. **一个 scheduler**：Kernel 提供触发机制（何时），Nox 做决策（为何/做什么）
4. **Nox 是类别不是清单**：定义是"认知与行为决策的插件组合"，
   人格/记忆/感知/Attention/Intent/Session Manager/Relationship
   只是目前的组成部分
5. **插件是统一机制，不是强制同构**：不同形态插件共用注册/生命周期/
   依赖/权限规则，内部实现允许不同；避免"为了插件化而插件化"
6. **外部插件边界清晰**：Memory/Health/HA/Body/Bridge 全在 Kernel 外，
   通过标准接口连接——换内核不拆 Caelum
7. **状态可见 = observable state**：mode/activity/attention/next_action
   结构化字段；模型 reasoning 永不外露
8. **干活能力复用内核工具**：不另造轮子，Nox 直接接
