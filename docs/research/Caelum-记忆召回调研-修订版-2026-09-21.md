# 记忆召回失效调研（修订版）

> 2026-09-21。初版 + 外部第二意见 + 用数据复核后的合并版本。
> 所有数字有离线复现脚本；标 ⚠️ 的是未验证的推测。
> 相对初版的改动集中在第四、五节 —— **架构判断变了，不只是补充**。

---

## 〇、一句话

**他不是没有记忆，是没有回忆能力。**
经历 → 理解 → 索引 → 召回 → 回应 这条链，后三节全断了：
索引层不存在面向检索的表示，召回层 98.7% 不启动，启动了也 94% 捞错。

---

## 一、系统结构

```
她说一句话（40–55 轮/天，已积累约 6400 条）
   ↓
[1] 理解层 appraisal    这句话底下有没有「值得记挂的事」
   ↓ 有 → Registry（活跃关注）→ 可能触发主动关心
   ↓ 没有 → 丢弃
   ↓
[2] 检索层 provider     每轮决定要不要翻长期记忆
   ↓
[3] 长期记忆            263 个「记忆桶」，每桶是一段 LLM 写的
                        第三人称摘要，带标题/领域/重要度
```

用户主诉：**「他有时候该躲还是躲，主动 recall 的情况比较少」**

---

## 二、三个实测发现

### 发现 1：98.7% 的轮次不翻记忆

检索层由一个分类函数决定是否加载，两个触发条件命中其一：

- ① 理解层报告「他心里正搁着一件事」（活跃锚点）
- ② 正则匹配到她字面说了「记得 / 上次 / 以前 / 那时候」

代码注释写明 **① 才是主路**，但理解层仍在 shadow（不写库），① 恒为 False。

拿她 9 月真实的 1072 句，直接 import 真实分类函数实测：

```
现状              14 / 1072 = 1.3%
若理解层转正      1072 / 1072 = 100%
```

### 发现 2：翻的时候 94% 捞错

离线复刻检索器（照抄真源码，并用**差分测试**把真实现 import 进来逐条比对
score 与排序，12 条查询三路全一致）。

**对照实验**：302 组「这句话当天确实沉淀成了那个桶」，同一检索器，只换问法：

| query | 捞回目标桶 |
|---|---|
| 她的原话（= 现在的做法） | **6.3%** |
| 桶自己的标题 | 99.0% |

⚠️ **99% 这个数的用途被修正了**（见第三节）：它只能证伪「检索器坏了」，
**不能**证明标题是好 query。真正可用的结论只有 6.3%。

**症状不是空，是满屏不相干**：捞空率仅 3.3%（且全是 `•ᐔ•` 这类无内容输入），
**86% 返回满额 6 条**。

> 她说「昨天晚上没睡好」
> 捞回：今晚约看机器人之梦 / 待办开发merge工具 / 小克的愿望清单 / 健身饮食记录系统
> 当天实际沉淀的 4 个桶一个都没捞到

**根因**：桶正文是第三人称 LLM 摘要，打分却拿她的第一人称口语原话去模糊匹配。
她的原话与最相似桶正文 `partial_ratio` 中位数 **31.6**，逐字锚点 0/150。

**下限检查**（拿桶自己的文字问自己，248 桶全量）：

```
用标题问        recall@6 = 91.1%
用正文第一句问  recall@6 = 71.8%   ← 桶自己写的话喂回去仍 1/3 捞不回自己
```

**三个附带的洞**：

1. 关键词通道 **45.3% 的查询返回 0 条**（阈值 50，而不带 topic 维度时
   理论天花板只有 41.2）。实际 **88.4% 的结果纯靠 BM25 撑着**。
2. 带英文撇号的输入触发 `fts5: syntax error`，异常被静默吞掉 →
   整条 BM25 通道失效。150 条里崩 11 条（7.3%）。
3. **14% 的桶标题就等于自己的 UUID**，领域「未分类」——
   标题×3 + 领域×2.5 共 5.5/8.5 权重对它们恒为 0。

### 发现 3：对话归档从未运行

归档模块（对话压成摘要写入长期记忆）实现完整、有测试，**零调用方**。
项目文档早有记录「已有，但要前端主动调」，挂了一个半月。

现有 263 个桶全部靠 AI 在对话中**当场想起来存**，没有兜底工序。

归档门槛本身的问题：
- 少于 3 轮用户发言不归档 → **两轮说完的大事永远不归档**
- 纯图片轮次因文本为空被过滤，摘要提示词也不含图片
- 只看最近 40 条；更早内容由压缩器合成的摘要因 `role="system"` 被过滤，
  **无补偿路径**

## 三、结论的边界（哪些不能信）

**a. 离线复刻缺向量通道。** 线上是关键词 + BM25 + embedding 三路融合，
备份无向量索引且不许连线上，所以 6.3% 只反映两路。
⚠️ 线上真实值更高，**高多少两种意见分歧**：初版作者猜「明显更高」，
第二意见猜「20–40%，不会到 90%，因为这是表达层问题不是语义距离问题」。
**双方都是猜测 —— 拿到线上 `embeddings.db` 离线副本即可实测，应当去测而不是争。**

不受影响的两条：关键词通道 45.3% 返回 0、桶正文喂回自己仍 1/3 失败
（单通道体检，与向量无关）。

**b. 99% 那个对照有设计缺陷。** 用标题查标题本质是「用答案找答案」，
只证明检索算法能匹配语言一致的东西。更公平的设计应是三组对照：

```
A 组：用户真实原话
B 组：人工写的「未来可能触发这个记忆的话」
C 组：LLM 生成的第一人称索引
比较 recall@k / precision@k / false recall
```

**c. 初版只测 recall，没测 precision —— 这是方法错误。**
陪伴型场景 **precision 比 recall 重要**：错想起比没想起更破坏体验。

**d. 其余**：脱水只走本地缓存、时间维度钉死、「同日沉淀」是弱标注非金标准
（但对照实验两边同标注，误差相减）。

## 四、架构判断（本次修订的核心，相对初版有实质改变）

### 4.1 🔴 归档应该是主入口，不是补充

> 大量重要记忆是**事后**形成的。今天「我妈检查结果出来了」当下未必写记忆；
> 三个月后她说「最近压力好大」，这时才需要知道三个月前发生过什么。

现在的模式是「她说一句 → AI 当场判断 → 马上存」，人脑不这么工作，
也没人每天主动整理「今日重要事件如下」。应改为：

```
对话流 → （每天 / 每几小时）反思 → 记忆候选 → 长期记忆
```

**这同时解释了理解层为什么只有 53% 精确率**（见附录）：
**它在试图实时做一个本该回溯做的判断。** 当下判不出来的事，事后才看得清。

### 4.2 🔴 「理解层」和「召回触发」应当解耦

现在「要不要翻记忆」取决于「AI 心里有没有搁着事」。这是错的耦合：

> 「今天好累啊」→ 理解层判不值得记
> 但召回层应该想到：**她最近连续加班，这是第三次说累**

那不是「记忆事件」，是「状态趋势」。人也不是因为「昨天发生过重要事」才回忆，
是**当前刺激触发关联**。

补充论据：理解层精确率只有 53%，**把召回挂在一个 53% 的信号上本身就不该**。

拆成两个模块：

```
Appraisal      这件事值得长期关注吗？
Memory Trigger 当前对话有没有理由查历史？
```

### 4.3 修检索：给记忆加入口，而不是让 query 去适配数据库

两条路线，**选后者**：

| | 每轮 LLM 改写 query | 写入时生成检索索引 |
|---|---|---|
| 成本 | 一年约 1.4 万次调用 | 263 桶各一次 + 新增时一次 |
| 延迟 | 加在对话主路径上 | 不在主路径 |
| 风险 | **幻觉**：「今天又没睡好」被改写成「长期睡眠障碍并担忧健康」→ 召回一堆医疗记忆 | 覆盖面受限于写入时的想象 |

> 陪伴型 AI 最大的问题不是找不到，而是**想太多**。

具体做法是给每个桶补充：

```
first_person_index:  "我最近毕设压力很大" / "论文让我睡不好"
possible_triggers:   熬夜 / 压力 / 毕业 / 不想做了
emotional_context:   焦虑 / 疲惫 / 逃避
```

这是 RAG 的标准做法：**不要让 query 去适配数据库，让数据库提供更多入口。**

### 4.4 理解层的判据应当是三维，不是一维

初版把判据从「她现在难不难受」改成「这件事明天还在吗」，**净效果为零**
（精准修掉 5 条「当下情绪」，又放进 5 条调情玩闹）。单维不够，应拆成：

```
1. Persistence        明天还成立吗？
2. Relationship impact 会不会改变两人的互动方式？
3. Future utility     未来什么时候想起它会有帮助？
```

⚠️ **但这个框架的示范判错了，我方用标注数据顶回去了**：

第二意见举例「今天肚子疼 → 三维全低 → 不记」。实际标注是：

```
[记]    睡会 头疼          [不记]  没练多少 小腹疼
[记]    快来姨妈了          [不记]  啊好累
[记]    回去了 膀胱炎       [不记]  讨厌 我睡不着了
```

**身体的事她一半标了记。** 界线不在「是不是身体」，
更像在**「会持续/会复发的状况」vs「此刻的一下」** ——
膀胱炎是诊断，姨妈是周期，训练时小腹疼是一过性。

框架方向认可，示范需要用真实标注重新校准。**150 条标注现成，可直接验。**

## 五、修复顺序（已按第二意见重排）

```
P0  修 retrieval representation —— 给记忆桶加第一人称检索索引
P1  接通归档，但降低门槛（3 轮 / 图片 / 40 条窗口都要改）
P2  拆开 appraisal 与 recall trigger
P3  理解层重做（三维判据 + 回溯式而非实时）
```

**关键判断：现在不要花时间调理解层的提示词。**
因为即使理解层做到 100 分，他也不知道怎么把记忆找回来。

**同时：现在不能让理解层转正。** 转正 = 从「98.7% 不翻记忆」变成
「100% 翻记忆但 94% 捞错」，每轮往上下文塞 6 条不相干旧事，比现状更糟。

### 关于「今天是不是白干了」

本次调研从理解层入手（现被排为 P3）。但正是测理解层时顺着
`has_understanding` 这条线摸到了 1.3%，才建了评测台，才测出 6.3%。
**是 P3 把 P0 暴露出来的。** 顺序从现在起倒过来。

## 六、下一步（可立即执行，均不需用户参与）

1. **拿 150 条现成标注跑三维判据**，验第二意见的框架是否真比现行单维分得开。
   零新标注成本。
2. **给 263 个桶生成第一人称检索索引**，重跑评测台，盯回归基准
   `recall_query_is_her_words`（现为 **0.0629**）是否变动。
   这是 P0 的最小验证，一次性 263 次调用。
3. **补 precision / false recall 指标** —— 现有台子只测 recall，按第二意见
   这是重点搞错了。

待办（需要额外条件）：
- 取得线上 `embeddings.db` 离线副本，实测向量通道究竟把 6.3% 抬到多少
- 修那三个洞：模糊匹配阈值 50、fts5 撇号崩溃、14% 桶名是 UUID

## 附录：理解层的实测数据

150 条人工标注：

- **精确率 53%**（说「该记」的 17 条里对 9 错 8），召回 9/12
- 同一提示词跑三次，抓到数在 **7/12、8/12、11/12** 之间飘（模型自身不稳定）
- 自报 confidence **判对时 0.790、判错时 0.762**，差 **0.027**
  → 拿它当阈值筛不出任何东西；77 条里**一次都没报过低于 0.5**
- 三次多数票可把误记从 10 压到 8（已实现，默认 3 次，可配）

错的 8 条有清晰模式：**模型把「当下情绪」当成了「要记住的事」**。
它读得都对 ——「我刚才真的气死了」确实在生气 —— 但用户认为说完就过去了。

**这个偏差与 4.1 是同一个问题**：当下无法判断一件事会不会留下来。
